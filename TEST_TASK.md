# Тестовое задание — Unity Developer

Необходимо с нуля разработать небольшой мобильный Unity-проект **Mini Factory**.

Нам важно увидеть не только итоговый результат, но и организацию проекта, архитектурные решения, работу со сторонней интеграцией, мобильным lifecycle, Git и AI-инструментами.

## Технические требования

- **Unity:** 6000.3.22f1
- **Платформа:** Android
- **IAP:** Unity IAP v5

Художественная составляющая не оценивается. Можно использовать стандартный Unity UI, primitives и бесплатные ассеты.

---

## 1. Mini Factory

На одном экране находится фабрика минимум из **3 производственных машин**.

Каждая машина имеет:

- состояние `Locked` / `Unlocked`;
- уровень;
- производительность;
- стоимость открытия;
- стоимость следующего улучшения.

Первая машина доступна сразу. Остальные открываются за игровую валюту.
Открытые машины автоматически производят валюту.

Игрок должен иметь возможность:

- открывать машины;
- улучшать их;
- активировать временный Boost.

На UI должны отображаться: баланс, общая производительность, состояние и уровень машин, цены и состояние Boost.

**Формулы экономики выбираются самостоятельно.**

## 2. Boost и offline progress

- Boost временно увеличивает производство всей фабрики.
- Его продолжительность и множитель должны задаваться через конфигурацию.
- Прогресс должен корректно учитывать сворачивание и повторный запуск приложения:
  - фабрика производит валюту offline;
  - offline production имеет максимальную продолжительность;
  - активный Boost учитывает реально прошедшее время.
- Прогресс игрока должен сохраняться между запусками.
- **Способ хранения выбирается самостоятельно.**

## 3. Конфигурация

Игровые параметры должны быть вынесены из gameplay-кода.

Минимально конфигурируются:

- параметры машин;
- стоимость открытия машин и параметры расчета стоимости улучшений;
- Boost duration;
- Boost multiplier;
- возможность включить/выключить Boost;
- максимальное время offline production.

Игра должна иметь локальную конфигурацию и быть спроектирована так, чтобы источник конфигурации в дальнейшем можно было заменить или дополнить Remote Config **без изменения игровой логики**.

## 4. Unity IAP

Подключите Unity In-App Purchasing.

Необходимо реализовать один consumable-продукт, например: `coins_pack_small`.

Успешная покупка начисляет игроку игровую валюту.

Для проверки достаточно использовать **Fake Store** — создавать настоящий продукт в Google Play не требуется.

Необходимо корректно обработать:

- инициализацию IAP;
- получение продукта;
- успешную покупку;
- неуспешную покупку;
- ситуацию, когда IAP недоступен или не инициализировался.

**Игровая логика не должна напрямую зависеть от API Unity IAP.**

## 5. Analytics

Реализуйте систему аналитических событий.

Минимальный набор:

- `game_started`
- `machine_unlocked`
- `machine_upgraded`
- `boost_started`
- `boost_finished`
- `offline_income_applied`
- `purchase_succeeded`
- `purchase_failed`

События должны содержать полезные параметры там, где это уместно.

Архитектура должна позволять одновременно подключать несколько Analytics Providers.

В обязательной части достаточно реализовать один Console/Debug provider.

**Gameplay-код не должен зависеть от конкретного Analytics SDK.**

## 6. Unit tests

Добавьте минимум **3 unit-теста** для логики, которую считаете наиболее важной.

Какие именно сценарии тестировать — решите самостоятельно.

## 7. Архитектура

Ограничений на конкретную архитектуру, DI framework или структуру каталогов нет.

Выберите решение, соответствующее масштабу задачи.

Мы будем обращать внимание как на связанность систем, так и на **необоснованный overengineering**.

## 8. Использование AI

Использование AI разрешено и приветствуется.

Необходимо использовать хотя бы один AI coding agent, способный работать непосредственно с кодовой базой.

Ограничений на количество кода, созданного AI, нет.

При этом кандидат должен быть готов объяснить любой код и самостоятельно аргументировать итоговые технические решения.

В корне репозитория добавьте `AI_USAGE.md`, где кратко укажите:

- какие AI-инструменты использовались;
- какие задачи им передавались;
- несколько ключевых промптов;
- какие части были реализованы с помощью AI;
- что было сделано самостоятельно;
- какие предложения AI были изменены или отклонены;
- какие ошибки или спорные решения AI удалось обнаружить, если такие были.

## 9. README

В корне репозитория должен находиться `README.md`.

Он должен позволить другому разработчику быстро понять проект и содержать как минимум:

- инструкции по запуску и Android build;
- описание основных систем и архитектурных решений;
- использованные packages/SDK;
- известные ограничения или незавершенные части;
- устройство или эмулятор, на котором проверялся build.

## 10. Git

Разработка должна вестись в Git-репозитории.

Ожидается использование **GitFlow** и формата **Conventional Commits**.

Репозиторий должен содержать понятную историю изменений и отражать реальный процесс разработки.

Используйте корректный `.gitignore` для Unity. Не добавляйте временные директории и build artifacts в репозиторий.

## Время выполнения

На выполнение задания необходимо потратить **не более 5 часов** фактической работы.

Срок сдачи — до **3 календарных дней** после получения задания.

Если за 5 часов обязательная часть не завершена, остановите работу и сдайте текущее состояние проекта.

В README укажите:

- примерное фактическое время работы;
- что осталось незавершенным;
- что вы сделали бы следующим шагом.
